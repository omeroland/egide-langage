## Question

**Executive summary.** A derivation "returns implementation items" (CT-030) and a template function "returns an
expression" (CT-040). No chapter defines the type of those values, how they are built, or how names in them resolve. This
is the whole design of the metaprogramming facility, and ADR-0004's claim "no macros" depends on what it turns out to be.

## Core analysis

*Established*: CT-020 gives read-only reflection; CT-030/CT-040 say the result is "type-checked as if written by hand";
CT-060 prints it. *Extrapolated*: a comptime function that returns code is a procedural macro without I/O. The open
points are the ones every macro system answers: hygiene (can generated code capture a caller's local?), spans for
diagnostics inside generated code, and whether generated code can name private items of the type's module.

| Option | Behaviour | For | Against |
|--------|-----------|-----|---------|
| A | a typed builder API in `std.meta` (`Impl`, `Method`, `Expr` values built by functions); no quotation syntax; names resolve in the scope of the annotated declaration; fresh names are generated by the API | no new syntax; hygienic by construction; auditable | verbose derivations |
| B | quotation syntax (`quote: … $x …`) | readable derivations | a second language inside the language, which ADR-0004 rejected |
| C | derivations return source text that is re-parsed | trivial to implement | unhygienic; spans lost; injection through type and field names |

## Recommendations / Next Steps

A, in an ADR before phase 2 is split. Reject C on security grounds (generated source built from identifiers and
attribute strings). The ADR must state the hygiene rule and what `egide expand` prints.
